# eval —— 话术与判定质量的评测器

**独立项目**，不参与插件运行。删掉整个 `eval/` 目录，插件照常工作。

## 为什么分开

插件是产品，这里是量尺。混在一起会有两个后果：

1. 测试代码混进发布包
2. 为了测试方便给产品加钩子，产品越改越脏

**依赖方向是单向的：`eval → web`，`web` 永远不知道 `eval` 存在。**

唯一的耦合是读取 `web/prompts.js` 和 `web/skills/greeting.js` —— 因为它们**就是被测对象**，不读它们就没有测试可言。

**绝不读取 `web/app.js`。** 早先的版本从 `app.js` 里切片取函数，`app.js` 一改测试就静默失效，这是隐性耦合，已经拆掉了。

## 三层评分

| 层 | 谁做 | 测什么 | 能否作弊 |
|---|---|---|---|
| L1 硬规则 | 纯代码 | 字数、寒暄词、抄示例、编造条件、缺口可追溯、专业开场 | 不能 |
| L2 集合级 | 纯代码 | 开头词分布、话术两两相似度、评分极差、身份分布 | 不能 |
| L3 判官 | 另一个模型 | 像不像真人发的 | 能，权重最低，暂未接入 |

**为什么必须有 L2：** 逐条打分永远发现不了"所有话术都用同一个开头"。每条单独看都切题、通顺、合规，全都能拿高分；20 条摆在一起才看得出模板化。用户最在意的失败模式恰恰是集合级的。

## 跑法

```bash
# 0. 自检：验证评测器本身是准的，不花 token
node eval/selftest.js

# 1. 只看 JD 筛选对不对，不调模型、不要 key
node eval/run.js --jds dev/jd.jsonl --limit 12 --dry

# 2. 正式评测（需要事实库和 API Key）
node eval/run.js --fact factbase-2026-11-19.json --limit 20

# 3. 留出集验证（调参时绝对不要看这批）
node eval/run.js --fact ... --limit 20 --split holdout
```

前置：面板「事实库 → 导出」拿到 `factbase-*.json`，并在 `eval/.env.local` 写一行：

```
DEEPSEEK_API_KEY=sk-xxxx
```

## 输出

```
eval/out/summary-<时间>.txt    人读的结论
eval/out/report-<时间>.json    全部原始数据
eval/out/samples-<时间>.csv    Excel 可打开
```

`summary` 里最该看的两块：

```
=== L1 硬规则 ===        平均分 / 哪几项在失败
=== L2 集合级 ===        开头 top1 占比 / 熵 / 两两相似度 / 评分极差
=== 报警 ===            超阈值的项，带具体数字
```

## 报警阈值

不是凭感觉定的，是「人正常写 20 条也不会这样」的量级：

| 指标 | 阈值 | 含义 |
|---|---|---|
| `openingTop1` | > 40% | 开头模板化 |
| `openingEntropy` | < 2.0 | 开头分散度不足 |
| `avgSimilarity` | > 35% | 换 JD 没换话 |
| `scoreSpread` | < 15 | 评分没区分度 |

## 样本切分

按公司轮转交错后，用索引取模切分：**5 条里留 1 条 作为 holdout**。

- `--split tune`（默认）：80%，调 Skill 时看这批
- `--split holdout`：20%，**只在最后验证时看一次**

调参时偷看 holdout，等于背答案。这套机制的唯一价值就是防这个。

## 已知限制

1. **没有结果标签**。HR 到底回不回复，公开数据拿不到。所以这里测的是「有没有犯低级错误 + 模板化程度」，不是「能不能拿到面试」。
2. **JD 分布偏**。312 条里 95% 是社招 3–5 年岗，校招只有 16 条。在你的真实战场（校招）上，指标可能更好也可能更差，这里测不出来。
3. **`compactForEval()` 是 `app.js` 里 `compactFactBase()` 的镜像**。分开的两个项目只能各写各的，改了插件记得同步这里，否则评测结果会和真实行为不一致。
